01 The problem

A result is a file. How it was made is somewhere else.

It lives in a shell history, a notebook, a workflow run, an email, a colleague’s memory.

Months later, or after a handover, the file is still there and the explanation is gone. Comparing two analyses means opening two folders and reading parameters by eye.

The usual defence is discipline: a README, a folder naming scheme, a careful person. It works until that person leaves, or the pipeline runs on a cluster nobody can reach from outside.

02 The idea

One record of how every result was made, around the pipelines you already use.

A pipeline engine knows what happened inside one pipeline. The story of a result is wider than that. Jubilab is building one record that spans all of it.

  1. Before the pipelineThe samples, the experiment context, the data preparation and the references that go in.
  2. Around the pipelineNextflow, Snakemake, scripts, notebooks and the manual steps in between.
  3. After the pipelineThe results, the analysis that follows and the decisions made from it.
It links, it does not copy.
Your data stays where it lives. Jubilab keeps pointers and context.
History cannot be edited.
A new run is a new record. Nothing is overwritten.
It claims no more than it knows.
Jubilab does not claim to make a result reproducible. It records what happened and shows what is missing.
03 In practice

What it makes possible.

Real screens and a real command session, all on synthetic demo data.

  1. Trace a result

    Start at any output and follow it back to the run that made it and the inputs that run used. Start at an input and see everything that depends on it.

  2. See what changed

    Line up two runs and see which parameters, versions or results differ. Jubilab records the difference. It does not decide which result is better.

  3. Know how sure you are

    A gap shows up as a gap. Ask a question and the answer is built from recorded evidence, or Jubilab says it cannot determine.

    • verified
    • inferred
    • manual
    • unknown

  4. Work offline, keep data in place

    On a cluster node with no internet, records are written to a file and synced later. The server runs on your machine and makes no outbound network calls.

04 Direction

Where this is going.

This section is direction, not a description of the product today. The proof above is what is demonstrated.

We are building the layer around pipelines for lab science: one trustworthy record from the sample to the decision, across the tools a lab already uses.

Genetics and genomics researchers are the first audience, because they often re-run the same analyses with changing parameters, and often work where data cannot leave the institution. Jubilab does not replace your pipelines and does not store your data.
