Guide

What parameters produced this result?

Look at the run's own records first. Nextflow keeps the launch command in .nextflow.log and nextflow log, Snakemake keeps the rendered shell command in .snakemake/metadata, and a plain shell keeps only what its history file kept. The catch is that several of these records store a file name, not the values inside the file, so a params file that was edited afterwards takes its answer with it.

Last reviewed 19 October 2026. Tested by us with Nextflow 24.01.0-edge and 25.10.0, Snakemake 9.27.0 and bash on small synthetic examples. Other versions may behave differently.

This guide is for the moment someone asks which settings produced a result and the person who ran it is not around, or was you six months ago. It works through the three common cases: a Nextflow run, a Snakemake run and commands typed in a shell. It then lists what a good record contains. Nothing here needs Jubilab.

Before you start: pin down the run

Work out which run made the file. The modification time of the output narrows the search, and for Nextflow the task hash in the work directory name (for example 36/005c4f) links a file back to its run. Write the answer down before reading logs, so you do not mix up two runs from the same folder.

Nextflow

Step 1: list the runs in this directory

Run from the directory the pipeline was launched in

nextflow log

Output from a test run (columns re-spaced here; the real output is tab-separated)

TIMESTAMP           DURATION  RUN NAME        STATUS  REVISION ID  SESSION ID                            COMMAND
2026-10-19 00:38:49 2.1s      jovial_swirles  OK      bdf3ef2c15   9c3c51ee-b5c7-4f0a-9c68-5104219813b9  nextflow run main.nf -params-file params.yml --min_q 20 -with-trace -with-report -with-timeline

The official documentation describes nextflow log as the command that prints the execution history. The command column is the part that answers your question: it holds the launch command, including any -params-file and --name value overrides.

Step 2: read the effective values, not only the command

Nextflow applies parameters from several places. The documentation gives the order, lowest to highest priority: defaults in the script, parameters in the configuration, parameter files given with -params-file, and command-line parameters (--foo bar). In the test above, params.yml said min_q: 30 and the command line said --min_q 20, so the run used 20. The command line alone does not show the 30 that was overridden, and the file name does not show what the file contained.

Line 1 of the log repeats the launch command

head -1 .nextflow.log
Oct-19 00:38:49.451 [main] DEBUG nextflow.cli.Launcher - $> nextflow run main.nf -params-file params.yml --min_q 20 -with-trace -with-report -with-timeline

In my test with Nextflow 24.01.0-edge, the log, nextflow log and the HTML report (-with-report) all stored the command line and none stored the values read from params.yml. The report summary shows the launch command, as its documentation says; it does not copy the file.

Step 3: ask what each task ran

Per-task fields for one run (use your run name)

nextflow log jovial_swirles -f 'hash,name,status,exit,script'
36/005c4f	COUNT	COMPLETED	0	wc -l < sample.txt

The field list comes from the documentation (nextflow log -l prints all of them). Each task also leaves its exact script in its work directory:

The script a task ran, with values already filled in

cat work/36/005c4f*/.command.sh
#!/bin/bash -ue
wc -l < sample.txt

Task scripts show parameters that ended up inside commands. They do not show parameters that only changed a branch of the pipeline.

Step 4: Nextflow 25.04 and later can store the resolved values

Nextflow added an experimental data lineage feature in 25.04. The documentation says it may change in future releases. With lineage.enabled = true in the configuration, each run writes a record that includes the parameters and the resolved configuration. In my test with Nextflow 25.10.0 the record held the value that won, 20:

Explore the lineage store (kept in .lineage by default)

nextflow lineage list
nextflow lineage view lid://<lineage id from the list>

Excerpt of the WorkflowRun record from the test

"params": [
  {
    "type": "Integer",
    "name": "min_q",
    "value": 20.0
  },
  {
    "type": "String",
    "name": "input",
    "value": "sample.txt"
  }
],

Going forward: save the params file with the results

The simplest habit is to copy the parameter file next to the outputs, named for the run. This snapshot is what I ran on the test project:

A minimal snapshot before launching

RUN=run_$(date +%Y%m%d_%H%M%S)
mkdir "$RUN"
cp params.yml main.nf "$RUN"/            # add your config files here
sha256sum sample.txt > "$RUN"/inputs.sha256
{ date -u +%FT%TZ; hostname; whoami; } > "$RUN"/env.txt

Snakemake

Snakemake takes its settings from the config file named in the Snakefile, from --configfile files, and from --config key=value overrides. The command-line reference says later config files overwrite earlier ones and --config sets or overwrites values in the config object. By default Snakemake stores provenance information in .snakemake/metadata, one small JSON record per output file.

List every output with its inputs, the shell command and a status

snakemake --cores 1 --detailed-summary --config min_q=20

Output from the test workflow (tab-separated)

output_file	date	rule	log-file(s)	input-file(s)	shellcmd	status	plan
out.txt	Mon Oct 19 00:40:11 2026	count		sample.txt	echo minq=20 > out.txt; wc -l < sample.txt >> out.txt	ok	no update

The shellcmd column shows the command with the parameter values substituted, which is usually the answer. The metadata record also holds the rule name, the params values, the input files with checksums and the start and end times. The log files in .snakemake/log record the Snakemake version and the date.

Watch the overrides. The value min_q=20 came from --config on the command line, not from config.yaml (which said 10). When I ran snakemake --summary afterwards without repeating --config min_q=20, the status was params changed, since the value now resolved to the 10 in the file. snakemake --list-changes params lists such outputs. The documented options for this are --summary, --detailed-summary and --list-changes {input,code,params}.

The documentation also describes an experimental database backend for this metadata (--persistence-backend db), with the warning "Use at your own risk", and --report for an HTML report with provenance information. Check the current manual before relying on either.

Plain shell commands

If the work was typed into a terminal, the history file is the record, and it is weaker than it looks. In bash, history entries carry no time stamps unless HISTTIMEFORMAT is set. Set it before you need it:

Keep time stamps with each command

# in ~/.bashrc
export HISTTIMEFORMAT='%F %T '

In my test, with the variable set, history -a wrote a # line with the epoch time above each command in the history file. Put real analyses in a script, keep the script under version control (git rev-parse HEAD gives the commit to note down), and run the script rather than retyping the commands.

What a good record contains

  • The exact command, and the values of every parameter that applied, not only the name of the file that held them.
  • A copy or checksum of each params and config file as it was on the day.
  • The pipeline version: a git commit or tag. For a pipeline fetched from git, note the tag or commit you passed with -r; nextflow run documents -r as the project revision (branch, tag or commit).
  • Versions of the tools and containers that ran, and the reference genome build and annotation release (how to check the build of a VCF or BAM).
  • The input files with checksums, and the output files with checksums.
  • Who ran it, when and on which machine.
  • What is not known. A field marked "unknown" is more useful later than a blank.

What gets lost

  • Params files are edited in place. The run records params.yml as a path. Change the file and the old values are gone from everywhere except your memory (shown above for Nextflow 24.01).
  • Logs are rotated. Starting another run in the same directory renamed the earlier log to .nextflow.log.1 in my test, and copying a project without its hidden files drops them.
  • Work directories get cleaned. nextflow clean is documented as cleaning up cache and work directories, and the task scripts live there.
  • Snakemake metadata describes the last run that wrote an output. Regenerate a file and the record of the previous run is replaced.
  • Overrides are not repeated. A --config value typed once is easy to forget the next time.
  • Environment is invisible. Module loads, environment variables and a container tag such as latest do not show up in a command line.
  • Manual steps leave no trace. A file renamed by hand, a spreadsheet edit or a filter applied in a notebook is outside all of the above.

How Jubilab helps

Available now

  • Records each run: the command, inputs, parameters and outputs, with an evidence status on every fact (verified, inferred, manual or unknown).
  • Trace a result back to its run and parameters; compare two runs to see which recorded values differ.
  • Runs are kept as history the application cannot edit.
  • Records Nextflow runs as they happen or imports a finished run, imports Snakemake runs, and records any other command with the native bash wrapper.
  • Opt-in capture of the reference genome and annotation details written in file headers. It ships with our next release.

Not available yet

  • Linking every sample to its files and results.
  • Checks that flag a sample swap or a reference genome build mismatch. These are not available yet.
  • Recovering runs that were never recorded. Jubilab records going forward; it cannot rebuild the history of a run it did not see.
