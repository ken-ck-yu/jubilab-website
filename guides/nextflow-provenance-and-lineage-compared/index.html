Nextflow provenance and lineage: what each tool records

Nextflow already records a lot about each run. nextflow log and the work directories show what ran, the trace, report and timeline show how it performed, and since Nextflow 25.04 an experimental lineage feature stores resolved parameters, configuration, inputs, outputs and checksums. Seqera Platform and Snakemake add their own records. This guide sets out what each one keeps, what it leaves out, and where a separate record beside them can help.

Last reviewed 19 October 2026 against the official documentation linked in Sources. Nextflow lineage is experimental and may change; check the current docs.

Statements about Nextflow, Seqera Platform and Snakemake below come from their official documentation as read on 19 October 2026, and the commands were run locally with Nextflow 24.01.0-edge and 25.10.0 and Snakemake 9.27.0. Product behaviour changes between releases, so treat the page as dated. Jubilab is not affiliated with Nextflow, Seqera or Snakemake, and this guide is not a ranking of them.

What Nextflow records

The log and the work directory

The documentation describes nextflow log as printing the execution history. Without arguments it lists runs, with a run name or session ID it lists that run's tasks, and -f chooses fields such as hash,name,status,exit,script. Each task has its own directory under work/, named from its hash, holding the staged inputs and the script that ran. The default cache is the .nextflow/cache directory in the launch directory.

Commands from the official reference, run in my test

nextflow log
nextflow log <run name> -f 'hash,name,status,exit,script'

Trace, report and timeline

The reports page lists four outputs: the trace file (a table with one row per task: times, CPU and memory), the HTML execution report (summary, resource usage, task table), the HTML timeline, and a workflow diagram. They are switched on with -with-trace, -with-report, -with-timeline and -with-dag or the matching config blocks. In my 24.01 test the files carried a timestamp in their names, as the current reference also shows. These are built to analyse and debug a run.

Switch on the reports for one run

nextflow run main.nf -with-trace -with-report -with-timeline

Data lineage (experimental, 25.04 and later)

The documentation describes lineage as tracking workflow runs, task executions and output files, each with a lineage ID (a lid:// URI). It is switched on in configuration and stores records by default in a .lineage directory in the working directory, unless lineage.store.location says otherwise.

Enable lineage

// nextflow.config
lineage.enabled = true

The subcommands the documentation describes (check verifies the checksum of an output record; it is listed on the CLI reference page for lineage)

nextflow lineage list
nextflow lineage view lid://<id>
nextflow lineage find type=TaskRun workflowRun=lid://<id>
nextflow lineage diff lid://<task a> lid://<task b>
nextflow lineage render lid://<id>/<file>
nextflow lineage check lid://<id>

Three kinds of record are described. A WorkflowRun holds the pipeline repository and revision, run name, parameters, resolved configuration and run metadata. A TaskRun holds the task name, script, inputs and software dependencies. A FileOutput holds the path, checksum, size, timestamps and links to the run and task that made the file. In my test with 25.10.0 a run with a params file and a command-line override recorded the value that won.

Limits the same page states: tasks that failed or were aborted are not recorded; files appear as workflow outputs only if they are published to the output directory; a resumed run is a distinct run that shares the original session ID; and a cached task does not produce a new TaskRun.

nf-prov

nf-prov is a Nextflow plugin that, according to the RO-Crate project page, generates provenance information for pipeline runs and supports BioCompute Object and Workflow Run RO-Crate output. I did not run it for this guide. It produces files per run, in formats other tools can read.

Seqera Platform

Seqera describes Platform as a platform available on-premises or in any cloud. Its getting-started documentation says the run detail page shows the configuration, parameters, status of individual tasks and the run report. Its data lineage page says the feature is in public preview, is supported in AWS compute environments, requires Nextflow 25.04 or later, AWS S3 object storage and Amazon Simple Notification Service, and is experimental and subject to change. I have not run Platform for this guide; these statements come from its documentation (version 26.2 of the Enterprise docs).

Snakemake

Snakemake stores provenance information in .snakemake/metadata by default. In my test with 9.27.0 this was one JSON record per output file, with the rule, input files and their checksums, the rendered shell command, the parameter values and the start and end times. --summary and --detailed-summary print a table of outputs, and --list-changes {input,code,params} lists outputs whose inputs, code or parameters changed since they were made. --report creates an HTML report with provenance information, and --archive packs the workflow under git control, inputs that the workflow did not create, and conda environments into a tar file. The metadata can instead be kept in a database with --persistence-backend db; the documentation marks this experimental.

Per-output provenance table

snakemake --cores 1 --detailed-summary

Where a separate record beside them can help

Each tool above records the runs of that tool, in its own place and format. A separate record is an addition, not a replacement: it does not ask you to change how you run Nextflow or Snakemake. It can help in these situations, and only these:

  • More than one engine, or no engine. A project with a Nextflow pipeline, a Snakemake workflow and a few shell scripts has three kinds of records and no single place that links them.
  • Records that outlive the working directory. By default the lineage store sits in .lineage, Snakemake metadata sits in .snakemake, and task scripts sit in work directories that nextflow clean is documented to remove. A record kept elsewhere survives a clean-up or a copied folder.
  • Steps outside any pipeline. A manual filter, a renamed file or a notebook step is invisible to a pipeline engine.
  • Saying how sure the record is. A value read from a log, a value inferred and a value typed in by a person are different kinds of fact. A record can keep that difference.
  • Older runs. Lineage needs Nextflow 25.04 or later, and runs made before it was enabled have no lineage records.

When you probably do not need one

If all of your work runs in Nextflow, you use 25.04 or later, you are comfortable with an experimental feature and the lineage store is kept safe, the built-in tools may answer your questions. Teams already on Seqera Platform with AWS lineage enabled get a web view as well. Check the limits in the table above against your setup before deciding.

What gets lost, tool by tool

  • Nextflow log: the contents of a params file (as the path only), and the whole log if the hidden files are not copied.
  • Trace and report: they are performance and debugging outputs; the report summary shows the launch command, not a copy of the params file.
  • Lineage: failed and aborted tasks, files that were not published to the output directory, and anything that ran before lineage was switched on.
  • Platform: runs launched outside it, and lineage outside the AWS setup described above.
  • Snakemake: the metadata of an earlier run once an output is regenerated, and any --config override you do not type again.
