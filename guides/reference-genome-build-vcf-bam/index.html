How to check which reference genome build a VCF or BAM used

Start with the file header: a VCF may carry ##reference and ##contig lines and a BAM carries @SQ lines, and the contig lengths in them tell GRCh37 from GRCh38. If the header is missing or you doubt it, compare contig names and lengths with a known reference, then test the REF alleles against a reference FASTA. Every command below was run on small test files, and none of them needs Jubilab.

Last reviewed 19 October 2026. Tested by us with bcftools 1.24 and samtools 1.24 on small synthetic test files. Other versions may print different output.

This guide is for anyone holding a variant or alignment file and wondering whether its coordinates are GRCh37 (also called hg19 or b37) or GRCh38 (hg38). The answer matters because positions from one build do not line up with the other, and merging or comparing files from two builds can give wrong results without any error message.

The quick answer: contig lengths

The length of chromosome 1 separates the two human builds. Chromosome 2 is a second check, and the mitochondrial sequence shows why hg19 and b37 are not interchangeable.

Step 1: read the VCF header

The VCF specification recommends that the header describes the reference and the contigs behind the data, so a well-behaved caller writes both. It does not require it, and a file can have been written by a tool that left them out.

Works in every bcftools version, and on BCF files

bcftools view -h sample.vcf.gz | grep -E '^##(reference|assembly|contig)'

Output from a small test file

##reference=file:///data/refs/GRCh38.primary.fa
##contig=<ID=chr1,length=248956422,assembly=GRCh38>
##contig=<ID=chr2,length=242193529>

Newer bcftools releases also have bcftools head sample.vcf.gz, which prints the header as written. It exists in bcftools 1.24 and is missing in 1.13, so the view -h form above is the safer habit. Without bcftools, a bgzipped VCF can be read with plain tools:

No bcftools needed (for an uncompressed .vcf use grep directly)

zcat sample.vcf.gz | grep -E '^##(reference|assembly|contig)' | head

What to look for:

  • ##reference= is free text. It is often a file path from the machine that made the file, such as the one above. A name in a path is a claim, not proof: a file called GRCh38.primary.fa can be a different sequence.
  • ##contig=<ID=...,length=...> gives one line per contig. The lengths are the most useful part, because they are hard to get wrong by accident. The optional assembly= attribute is a label the writer chose. The optional md5= attribute, which the VCF 4.5 specification defines as the MD5 checksum of the sequence (calculated as in the SAM specification), is the strongest header evidence when present, in the same way as the M5 tag in a BAM header. Many writers leave it out.
  • Tool lines such as ##bcftoolsCommand=mpileup -f GRCh38.primary.fa sample.bam record how the file was made, and the -f argument names the reference that was used. Not every tool writes such a line.
  • The viewing tool adds lines of its own. In my test, bcftools view -h appended ##bcftools_viewVersion and ##bcftools_viewCommand lines, and the bcftools manual says bcftools head may add a ##FILTER=<ID=PASS> line when it is missing. Do not read those as part of the original file.

Step 2: read the BAM or CRAM header

Header lines that name each reference sequence

samtools view -H sample.bam | grep '^@SQ'

Output from a small test file (fields are tab-separated)

@SQ	SN:chr1	LN:248956422	AS:GRCh38	UR:file:///data/refs/GRCh38.fa
@SQ	SN:chr2	LN:242193529

In the SAM specification, SN is the sequence name, LN its length, AS a genome assembly identifier, UR a URI for the sequence and M5 the MD5 checksum of the sequence. Of these, M5 is the strongest evidence when present, because matching M5 values mean the sequences are identical. Many aligners leave it out, and in my test file it is absent.

The program lines often show the aligner command, and with it the reference index

samtools view -H sample.bam | grep '^@PG'

One pitfall: samtools view -H adds a @PG line for itself to the output it prints (in samtools 1.24 it did, and --no-PG turns that off). Your terminal output is not byte-for-byte the stored header. For a quick list of names and lengths from the index, samtools idxstats sample.bam prints them with read counts.

Step 3: compare contig names and lengths with a reference

If the header has no build name, or you do not trust it, compare its contig list with the index of a reference FASTA you can name. samtools faidx writes that index, and its first two columns are name and length. These commands use GNU sed.

VCF header against a FASTA index

samtools faidx GRCh38.fa
bcftools view -h sample.vcf.gz \
  | sed -n 's/^##contig=<ID=\([^,>]*\),length=\([0-9]*\).*/\1\t\2/p' | sort > vcf.contigs
cut -f1,2 GRCh38.fa.fai | sort > ref.contigs
echo "in the VCF header but not in the reference:"; comm -23 vcf.contigs ref.contigs
echo "in the reference but not in the VCF header:"; comm -13 vcf.contigs ref.contigs

Output from a test file whose chromosome 2 was one base longer than the reference

in the VCF header but not in the reference:
2	31
in the reference but not in the VCF header:
2	30

Empty output from both comm commands means the VCF contigs and the reference match by name and length. A long list means a different build, a different naming scheme, or a reference with extra sequences such as alternate contigs.

The same listing for a BAM

samtools view -H sample.bam \
  | sed -n 's/^@SQ\tSN:\([^\t]*\)\tLN:\([0-9]*\).*/\1\t\2/p'

Output from the test BAM

chr1	248956422
chr2	242193529

To keep a compact fingerprint of the contig list, hash the sorted file you just made. Two files with the same hash have the same names and lengths.

Contig-list fingerprint

md5sum vcf.contigs

Step 4: when the header says nothing, test the REF alleles

Every VCF record states the reference base or bases at its position. Against the right FASTA they match almost always; against the wrong build many do not. bcftools norm --check-ref reports mismatches without changing the data (w means warn).

Try each build you suspect

bcftools norm --check-ref w -f candidate.fa sample.vcf.gz -o /dev/null

Output from a two-record test file in which one REF base was wrong

REF_MISMATCH	1	2	A	C
Lines   total/split/joined/realigned/mismatch_removed/dup_removed/skipped:	2/0/0/0/0/0/0

Newer bcftools versions print a longer norm summary line than the one above (bcftools 1.13 prints this shorter form), so expect different wording and extra counts on a current release. The REF_MISMATCH lines are the part to read.

Treat the result as evidence, not proof. A high share of mismatches suggests a different build. A handful can have other causes, and a file with only a few variants can match two builds by chance, so use as many records as you can.

For a PLINK .bim file this is the route to take: the format has six columns (chromosome, variant ID, genetic position, base-pair coordinate and two alleles) and no field for the assembly.

Pitfalls that cause wrong answers

The chr prefix

Some references name chromosomes chr1 and others 1. Compare a VCF using one style with a FASTA using the other and bcftools stops:

Output when the VCF says chr1 and the FASTA says 1

[E::faidx_adjust_position] The sequence "chr1" was not found
faidx_fetch_seq failed at chr1:1

The labels can be changed with bcftools annotate --rename-chrs map.txt, where map.txt has two columns (old name, new name). That renames labels only. It never converts positions from one build to another, which needs a liftover tool.

hg19 is not the same as b37

The chr1 lengths agree, so a quick look suggests the same build, but the names differ and so does the mitochondrial sequence (16,571 bases in UCSC hg19 against 16,569 in GRCh37; see the table). Mixing them can silently mismatch the mitochondrial calls.

One build name, many contig lists

When I counted the UCSC chromInfo files on 19 October 2026, hg38 listed 711 sequences, 351 of them with alt in the name, and hg19 listed 298. Two files that both say GRCh38 can still carry different contig sets, so a difference in the lists is a prompt to look, not proof of a different build.

A header that disagrees with the data

Headers are text that a tool wrote. A file can be converted, lifted over or edited without its header being updated. When the header and the REF check disagree, trust the REF check and find out how the file was made.

What to record so you never have to guess

  • The build name and the FASTA file used for calling or alignment, with its path and checksum (sha256sum GRCh38.fa).
  • How you know: header line, contig fingerprint (md5sum vcf.contigs) or REF check, and which command printed it.
  • The checksum of each input and output file, with the date and the person who ran the step.
  • The annotation release used downstream, if any, next to the build, because annotation is tied to a build too.
  • The exact commands, in a script kept with the data (guide on finding the parameters of a run).

What gets lost

  • Headers are dropped by anything that writes records without them, such as bcftools view -H, a table export, or a script that rebuilds the file.
  • A ##reference path points to a disk you may no longer have, and the name inside it may never have matched the content.
  • PLINK .bed/.bim/.fam sets, plain BED files and tables carry no assembly field at all.
  • When the build lives only in a folder name, a file name or someone's memory, it leaves when the file is copied or the person moves on.
  • Merging files copies one header and quietly discards the other.
