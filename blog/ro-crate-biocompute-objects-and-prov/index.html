RO-Crate, BioCompute Objects and PROV: which one?

If you search for how to share the history of a workflow run, three names come up again and again: PROV, RO-Crate and BioCompute Objects. They are often mentioned in the same breath, and they are not the same kind of thing. This post puts them side by side in plain words, using each project's own documentation, and ends with questions to ask yourself before choosing. One note up front: Jubilab does not import or export any of these formats.

By Jubilab · 19 October 2026 · 6 min read

provenance standards bioinformatics

Formats are not stores

A distinction helps before the details. A format says how to write a record down so another person or program can read it. A store is where records live and how you search them. Nextflow's lineage feature, for instance, keeps a store of records in a directory.[1] PROV, RO-Crate and BioCompute Objects are on the format side: they describe what a record should look like when you hand it over.

W3C PROV

PROV is a family of documents from the W3C. The overview lists a core data model (PROV-DM), an ontology that maps the model to RDF (PROV-O), a human-readable notation (PROV-N), an XML schema (PROV-XML) and several others for things such as constraints and linking.[2] The data model is built from entities, activities and agents: things, the processes that act on them, and those responsible.[3]

PROV is general. It was not written for sequencing, and it says nothing in particular about VCF files or aligners. That is a strength if you want a vocabulary that other communities understand, and a cost if you wanted a ready-made template for a pipeline run. Other specifications, including the two below, can build on it or sit beside it.

RO-Crate

The RO-Crate site describes it as a community effort to establish a lightweight approach to packaging research data with their metadata.[4] In the 1.1 specification, the core of a crate is a JSON-LD (a web data format) file named ro-crate-metadata.json, which uses common published vocabularies, chiefly schema.org, to describe the files, people and processes in the package.[5]

For workflow runs there is a set of profiles called Workflow Run RO-Crate. Its site names three: Process Run Crate, Workflow Run Crate and Provenance Run Crate, and lists several workflow systems that have implemented the profiles or plan to, with Nextflow and Snakemake shown against the Provenance profile.[6] We have not tried to read how much detail each profile expects, so we do not compare them here.

BioCompute Objects

A BioCompute Object, or BCO, is described by its documentation as an instance of a workflow written in conformance with a standard, and the standard is IEEE 2791-2020.[7] The IEEE listing gives its title as "IEEE Standard for Bioinformatics Analyses Generated by High-Throughput Sequencing (HTS) to Facilitate Communication", published 2020-05-11.[8] Its user guide says BCOs are represented as JSON and are organised into domains, including provenance, usability, description, execution, parametric, input and output, and error domains, plus an extension domain.[9]

Unlike PROV, then, this one is shaped for high-throughput sequencing analyses from the start, with named places for parameters and for inputs and outputs. How its provenance domain relates to the W3C model is something we have not worked through.

What nf-prov writes

Because the three are easy to confuse, a concrete tool helps. The nf-prov plugin for Nextflow generates provenance information for pipeline runs. Its documentation lists several output formats, including bco and wrroc, the Workflow Run RO-Crate format, which it marks as new in version 1.4.0; it also says an older legacy format was removed in version 1.5.0 and suggests considering data lineage instead.[10] So one plugin can write a BCO and an RO-Crate from the same run. We did not run the plugin for this post and do not know how the two outputs compare in detail.

A first choice, as questions

We would rather give you questions than a verdict.

  1. Who is going to read it, and what do they expect? If a repository, a collaborator or a journal asks for a specific format, that settles it. We have not found a journal policy to cite, so check the one you care about.
  2. Do you need to package files with the description, or only describe a run? RO-Crate is about packaging data with metadata. A description of a run alone may need less.
  3. Is the analysis high-throughput sequencing? BCO is shaped for that case; PROV and RO-Crate are broader.
  4. Does your engine already write one? If you use Nextflow, the plugin above may save work. If you use Snakemake, the Workflow Run RO-Crate site lists it, but we have not checked what that support covers today.
  5. Will you need to query the history, or only hand it over? None of the formats is a place to search. That is what a store is for.

It is also worth asking whether you need to pick at all. Some teams may keep an internal store and export a format when someone asks for one. We have not tested how smooth that is.

Where Jubilab is now

Nothing. Jubilab does not import or export PROV, RO-Crate or BioCompute Objects, and we are not claiming compatibility with any of them. The earlier prototype kept its own record, with a status of verified, inferred, manual or unknown on each fact. Jubilab's earlier run-record prototype is not being offered. Whether and how a record like that should map onto these formats is an open question for us, and we would want to talk to people who hand these files to others before deciding. For the vocabulary, see our post on provenance versus lineage and our guide on Nextflow provenance and lineage. Questions we are still asking

  • Which of the three do the people who receive your results actually open? We do not have evidence either way.
  • How much information survives a trip from a store into a format and back? We suspect something is lost, but have not tested it.
  • RO-Crate and BCO outputs from the same Nextflow run are possible with nf-prov. Do they agree on the facts they both describe? We have not compared them.
  • Would a record that marks each fact verified, inferred, manual or unknown fit into any of these formats without losing the marks? It is worth asking before building anything.
  • If the formats keep changing, with RO-Crate listing a newer release than the one we read, how should a lab decide when to move?
  • Is a lightweight format better for most labs than a thorough one? We do not know.
